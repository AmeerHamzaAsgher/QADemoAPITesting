# 4. Check Git status

```powershell
git status
```

Possible output:

```text
On branch main

No commits yet

Untracked files:
...
```

This is normal for a new Git repository.

### Why?

`git status` tells us:

* Current branch
* Whether commits exist
* Modified files
* Untracked files
* Staged files

---

# 5. Initialize Git

If Git has not already been initialized:

```powershell
git init
```

Possible output:

```text
Initialized empty Git repository
```

If you see:

```text
Reinitialized existing Git repository
```

Git was already initialized.

### Why?

This creates the `.git` directory that turns the project folder into a Git repository.

---

# 6. Set the main branch

```powershell
git branch -M main
```

### Why?

This establishes:

```text
main
```

as the primary branch.

### Important

If:

```powershell
git branch
```

shows nothing immediately afterward, that can be normal when the repository has **no commits yet**.

After the first commit, you should see:

```text
* main
```

---

# 7. Configure Git username

Check the current configuration:

```powershell
git config --global user.name
```

If empty, configure it:

```powershell
git config --global user.name "YOUR_GITHUB_USERNAME"
```

### Why?

Git stores the author name in each commit.

---

# 8. Configure Git email

Check:

```powershell
git config --global user.email
```

If empty:

```powershell
git config --global user.email "YOUR_GITHUB_EMAIL"
```

### Why?

Git associates commits with the configured email address.

---

# 9. Check Git history

```powershell
git log --oneline --decorate --all -10
```

For a new repository, you may receive:

```text
fatal: your current branch 'main' does not have any commits yet
```

This is normal.

### Why?

This verifies whether previous commits already exist.

Do not delete existing commits simply because the repository is being prepared for GitHub.

---

# 10. Check the GitHub remote

```powershell
git remote -v
```

If nothing appears, no remote repository is configured.

If you see:

```text
origin  https://github.com/USERNAME/REPOSITORY.git (fetch)
origin  https://github.com/USERNAME/REPOSITORY.git (push)
```

a remote already exists.

### Why?

The remote tells Git where to push the project.

---

# 11. Add the GitHub remote

If no `origin` exists:

```powershell
git remote add origin https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git
```

Replace the URL with the **actual GitHub repository URL**.

Example:

```powershell
git remote add origin https://github.com/AmeerHamzaAsgher/QADemoAPITesting.git
```

### Why?

This connects:

```text
Local repository
       ↓
origin
       ↓
GitHub repository
```

### Important

Never use a guessed repository URL.

---

# 12. Verify the remote

```powershell
git remote -v
```

Expected:

```text
origin  https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git (fetch)
origin  https://github.com/YOUR_USERNAME/YOUR_REPOSITORY.git (push)
```

### Why?

This confirms that both fetch and push operations point to the intended repository.

# 14. Search for sensitive information

Before staging files, search the project:

```powershell
Get-ChildItem -Recurse -File | Select-String -Pattern "password|api_key|apikey|client_secret|access_token|refresh_token"
```

Review the output carefully.

Never commit:

```text
Real passwords
Real API keys
Real access tokens
Real refresh tokens
Client secrets
Session cookies
```

Safe variables are acceptable:

```text
{{password}}
{{apiKey}}
{{authToken}}
{{refreshToken}}
```

### Why?

GitHub repositories can expose sensitive credentials.

---

# 15. Stage the project files

```powershell
git add .
```

### Why?

This moves the current project changes into Git's staging area.

The process is:

```text
Working Directory
       ↓
git add .
       ↓
Staging Area
       ↓
git commit
       ↓
Local Repository
       ↓
git push
       ↓
GitHub
```

---

# 17. Review staged changes

```powershell
git diff --cached --stat
```

This provides a summary of staged changes.

For a detailed review:

```powershell
git diff --cached
```

### Why?

This verifies that Git is about to commit what you actually intended.

Pay special attention to:

```text
postman/environments/
postman/collections/
```

and:

```text
docs/
```

because these may contain configuration or API information.

---

# 18. Create the commit

After confirming everything is correct:

```powershell
git commit -m "Complete Phase 3 Postman API implementation"
```

Example result:

```text
[main abc1234] Complete Phase 3 Postman API implementation
```

### Why?

A commit creates a permanent checkpoint in the local Git repository.

This commit represents:

```text
Phase 1
+
Phase 2
+
Phase 3
```

---

# 19. Verify the commit

```powershell
git log --oneline --decorate -5
```

Expected:

```text
abc1234 (HEAD -> main) Complete Phase 3 Postman API implementation
```

### Why?

This confirms that the Phase 3 project has been committed locally.

---

# 20. Push to GitHub

If the GitHub repository is empty:

```powershell
git push -u origin main
```

### What `-u` means

It establishes the upstream relationship:

```text
local main
     ↕
origin/main
```

After this, future pushes can usually use:

```powershell
git push
```

### Important

Do NOT use:

```powershell
git push --force
```

unless there is a specific, understood reason.

Force-pushing can overwrite remote history.

---

# 21. Verify local repository status

After the push:

```powershell

```

Ideal output:

```text
On branch main
Your branch is up to date with 'origin/main'.

nothing to commit, working tree clean
```

### Why?

This confirms:

* No uncommitted changes
* Local branch is synchronized with GitHub
* Working tree is clean

You should see:

```text
HEAD -> main
origin/main
```

both pointing to the same commit.

### Why?

This confirms the local and GitHub branches are synchronized.

# Security Rule

Never commit:

```text
Passwords
API keys
Access tokens
Refresh tokens
Client secrets
Private certificates
Session cookies
Production credentials
```

Use environment variables or secure secret-management mechanisms instead.

For Postman:

```text
{{authToken}}
{{apiKey}}
{{username}}
{{password}}
```

is preferable to storing actual secret values in the collection.
